# Does the Talker's loop run on workerd?

Research for [#123](https://github.com/chengchao/hopon/issues/123), part of map [#111](https://github.com/chengchao/hopon/issues/111). Researched 2026-10-16.

**Question:** Does Vercel AI SDK v7 `streamText` with tools, `stopWhen`, and the Anthropic provider pointed at the Cloudflare AI Gateway run inside a Durable Object on workerd (`nodejs_compat`)? Can a tool call await a Container binding fetch that streams for minutes? Which DO limits apply? Does pi-agent-core run on workerd as an alternative?

**Short answer: it works, no flags or shims beyond what `apps/api` already has.** A throwaway Worker (`ai@7.0.143`, `@ai-sdk/anthropic@4.0.82`, `zod@4`, `compatibility_date: 2026-09-01`, `nodejs_compat`) ran `streamText` with a tool, `stopWhen: stepCountIs(5)` and `createAnthropic({ baseURL: "https://gateway.ai.cloudflare.com/v1/<acct>/<gw>/anthropic" })` inside a SQLite-backed Durable Object under `wrangler dev --local` (workerd 1.20261012.1, wrangler 4.151.0). Two steps completed (tool_use, then text), the tool awaited a 2 s streamed body, and the provider posted to `.../anthropic/messages`, which is the gateway's Anthropic endpoint. `@earendil-works/pi-agent-core@1.3.0` also imports and bundles on workerd.

The limits that matter are wall time and eviction, not CPU. A DO request has unlimited wall time while the caller stays connected; CPU is 30 s per request by default, raisable to 5 min with `limits.cpu_ms`, and awaiting I/O does not consume it. Pending I/O keeps the object alive for at most 15 minutes per operation, which fits the 5-minute turn limit already decided in #111.

## Findings

### 1. The AI SDK on workerd

- `ai@7.0.143` declares `engines.node >= 22` and depends only on `@ai-sdk/provider`, `@ai-sdk/provider-utils` and `@ai-sdk/gateway` (`npm view ai`). It uses global `fetch` and web streams, which workerd provides natively. The AI SDK docs do not have a Cloudflare Workers page; the only Cloudflare mention in [Providers and Models](https://ai-sdk.dev/docs/foundations/providers-and-models) is the community `workers-ai-provider`. The local run is the evidence.
- `createAnthropic` takes `baseURL` (default `https://api.anthropic.com/v1`), `apiKey` (sent as `x-api-key`), `headers` and `fetch` ([Anthropic provider](https://ai-sdk.dev/providers/ai-sdk-providers/anthropic)). The provider appends `/messages` to `baseURL`, so `baseURL = https://gateway.ai.cloudflare.com/v1/{account_id}/{gateway_id}/anthropic` hits exactly the endpoint Cloudflare documents for Anthropic through AI Gateway ([AI Gateway: Anthropic](https://developers.cloudflare.com/ai-gateway/usage/providers/anthropic/)). An authenticated gateway wants `cf-aig-authorization: Bearer {CF_AIG_TOKEN}` through `headers`; with BYOK or Unified Billing, omit `x-api-key`. Cloudflare's own [Vercel AI SDK integration page](https://developers.cloudflare.com/ai-gateway/integrations/vercel-ai-sdk/) uses the `ai-gateway-provider` package instead of a raw `baseURL`; either works, and `baseURL` adds no dependency.
- Loop control: `stopWhen` "controls when to stop execution when there are tool results in the last step"; the loop also ends when "a finish reason other than tool-calls is returned". `prepareStep` runs before each step and can override `model`, `activeTools`, `toolChoice` or `messages` ([Loop control](https://ai-sdk.dev/docs/agents/loop-control)). The docs name the step condition `isStepCount`; `stepCountIs` is still exported from `ai@7.0.143` and worked in the check. The `fullStream` part types seen in order: `start, start-step, tool-input-start, tool-input-delta, tool-input-end, tool-call, tool-result, finish-step, start-step, text-start, text-delta, text-end, finish-step, finish`.
- Bundle: `ai` + `@ai-sdk/anthropic` + `zod` added ~1.68 MiB raw / 281 KiB gzip to the Worker (`wrangler deploy --dry-run`); adding `pi-agent-core` took it to 2.37 MiB / 380 KiB. Both are under the 10 MiB gzip Paid-plan script limit, but the Talker is bundled into the one `hopon` Worker, so the size lands on every request's cold start.

### 2. A tool awaiting a Container fetch that streams for minutes

- **Wall time:** "Unlimited" for a Durable Object RPC or HTTP request while the caller stays connected; Workers' HTTP requests likewise have no hard limit while the client stays connected ([DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/), [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)). The Container package documents no request-level timeout on `fetch()` or `containerFetch()`; its only timeouts are startup (`instanceGetTimeoutMS` 8 s, `portReadyTimeoutMS` 20 s). `sleepAfter` defaults to `10m` and incoming requests reset it; call `renewActivityTimeout()` for background work ([Container package](https://developers.cloudflare.com/containers/container-package/)).
- **Eviction while waiting:** pending I/O "prevents eviction until it completes or for up to 15 minutes from when it starts, whichever comes first": outbound `fetch()`, DO RPC, `waitUntil()`, timers, TCP sockets and outbound WebSockets all count ([DO lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)). The [2026-06-19 changelog](https://developers.cloudflare.com/changelog/post/2026-06-19-outbound-connections-keep-dos-alive/) made this explicit for agents streaming LLM responses: before it, an object with only an open outbound connection could be evicted after 70-140 s. A Coder call that streams longer than 15 minutes would stop pinning the object; the 5-minute turn cap in #111 keeps us well inside.
- **CPU time:** 30 s per request by default, "configurable to 5 minutes of active CPU time" for SQLite-backed objects via `limits.cpu_ms`; each incoming request or WebSocket message resets the budget ([DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/)). Awaiting a stream costs almost no CPU, and more than 30 s of compute between requests gives "a heightened chance that the individual Durable Object is evicted and reset". Parsing model SSE and relaying it is cheap; the default is enough unless the eval says otherwise.
- **Subrequests and connections:** 6 simultaneous outgoing connections per request (counted only until response headers arrive, so a streaming body does not hold a slot); 10,000 subrequests per request on Paid ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)). A turn of 12 steps makes ~12 model calls plus a few Coder calls, nowhere near either.
- **Durable Object requests cannot be cut short by a client disconnect alone:** `waitUntil` keeps work alive "until it settles or for up to 15 minutes" and "does not affect when a request or RPC completes" ([DO state API](https://developers.cloudflare.com/durable-objects/api/state/)). So the Talker can run the turn under `ctx.waitUntil` and relay to whichever client is attached, instead of tying the loop to one HTTP response.
- **Restarts:** during a runtime update in-flight requests get "up to 30 seconds to complete"; requests that touch storage after the restart begins return an error; WebSockets are terminated ([DO lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)). A multi-minute turn must therefore be resumable from stored state (Revisions, step log), not only in memory.

### 3. Hibernation vs an SSE relay

- Hibernation applies only when the object is a WebSocket **server** and needs: no timers, no unfinished I/O or `waitUntil`, no standard-WebSocket-API use, no request being processed; then it hibernates "after 10 seconds of inactivity" while clients stay connected. An idle object that cannot hibernate is evicted "after 70-140 seconds of inactivity" ([DO lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/), [WebSockets best practice](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)).
- Billing: duration is wall-clock "as long as the Object is active and not eligible for hibernation", charged for 128 MB regardless of use, shared across concurrent requests, $12.50/million GB-s after 400,000 included ([DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)). A non-hibernating `accept()`ed WebSocket "will incur duration charges for the entire time the WebSocket is connected"; an open SSE response is an in-flight request and bills the same way.
- Consequence for #111's decided transport (SSE + POST): during a turn the object is awake anyway (model stream, Coder fetch), so SSE costs nothing extra; between turns an open SSE keeps the object billed at 0.128 GB-s per second, about $0.0058 per hour per Draft past the free allowance. Hibernating WebSockets would bring that to zero but require the client to speak WebSocket. Cheap fix that keeps SSE: close the relay when the turn finishes and reconnect on the next POST. A DO `ReadableStream` response can be cancelled from the Worker and "the cancellation propagates to the Durable Object" ([example](https://developers.cloudflare.com/durable-objects/examples/readable-stream/)).

### 4. pi-agent-core on workerd

- `@earendil-works/pi-agent-core@1.3.0` depends on `typebox` and `@earendil-works/pi-ai@1.3.0`, `engines.node >= 22.19.0`; its README says nothing about Workers or edge, only browsers via `streamProxy` ([README](https://github.com/earendil-works/pi-mono/blob/main/packages/agent/README.md)). `pi-ai` pulls `@anthropic-ai/sdk`, `openai`, `@google/genai`, `@aws-sdk/client-bedrock-runtime`, `http-proxy-agent`, `https-proxy-agent` and `@smithy/node-http-handler` (`npm view`).
- The check: `import("@earendil-works/pi-agent-core")` resolved on workerd and exported `Agent, agentLoop, agentLoopContinue, runAgentLoop, runAgentLoopContinue, runToolCall, setDefaultStreamFn, streamProxy`. Nothing threw at import; the `[unenv] ... is not implemented` string did not appear in the bundle, so no stubbed Node API is on an import path. Under `nodejs_compat` `http`, `https`, `net`, `tls` and `stream` are real implementations; `child_process` and `worker_threads` are stubs that throw when used ([Node.js APIs](https://developers.cloudflare.com/workers/runtime-apis/nodejs/)).
- Verdict: it loads, but it was not exercised against a model and it costs +0.7 MiB raw (whole pi-ai provider set, no tree-shaking across the dynamic import) for a loop the AI SDK already gives us with `stopWhen`/`prepareStep`. The Coder keeps pi (pi-coding-agent in the Container, ADR 0003); the Talker does not need it.

## What the check did not cover

- No real model call, no real AI Gateway auth, no real Container binding: the Coder stream was a local `ReadableStream` with 400 ms gaps, the model was a stubbed Anthropic SSE body. The provider's request shape and the gateway URL were verified, not the gateway's response.
- Production workerd eviction and CPU accounting were taken from docs, not measured.

## Recommendation

Build the Talker as planned: AI SDK `streamText` + `stopWhen` in the per-Draft DO, Anthropic provider with `baseURL` at the gateway and `cf-aig-authorization` in `headers`. Run each turn under `ctx.waitUntil`, persist step results as they arrive, cap a Coder call below 15 minutes (the 5-minute turn already does), close the SSE relay between turns, and leave `limits.cpu_ms` at the default until the eval shows otherwise. Skip pi-agent-core for the Talker.
