# 8. Games are Vite projects in Phaser, React Three Fiber or React

## Status

Proposed. It builds on ADR 0006 (one agent, game making as a skill) and ADR 0007 (shared, frozen vendor files). It ends the authoring of LittleJS and plain-DOM games that ADR 0003 and ADR 0005 described.

## Context

The Maker wrote every game as one `game.ts`: LittleJS for games with motion, plain DOM for cards, quizzes and puzzles. ADR 0007 put Vite, React 19, Phaser 4, three and React Three Fiber in the box and on the Worker, and taught the harness to build and play a workspace with a `vite.config.ts`. The agent still wrote LittleJS and plain DOM, because its skills said so. The eval's judge scored the looks of those games about 3.1 to 3.7 out of 5: LittleJS draws flat shapes unless the model works hard, and it has no 3D at all.

## Decision

- **Three engines, one layout.** A new game is a Vite project: `index.html` loading `/hopon/v1.js` and then `src/main.tsx`, `vite.config.ts` with `@vitejs/plugin-react`, and one `tsconfig.json` whose `include` is `src`. 2D games with motion are Phaser 4.2.1, 3D games are React Three Fiber 9.8.2 on three 0.187.0, and card, quiz, word and puzzle games are React 19.3.1. A vague request gets a game with motion.
- **A Phaser game's panels are React.** A Phaser game that also has panels of words and buttons (a shop, an inventory, a dialogue) keeps its world in a Phaser scene and draws the panels as React DOM over the canvas. The bridge is a file, `src/panels.tsx`, that `node /opt/hopon/starter.js panels` writes into the workspace before the agent writes code: in the new-game command, or alone to add panels to a Phaser game. Its API holds the bridge's rules instead of a guide saying them: `showPanels(<Panels />)` renders the panels in their own React root over the canvas, never the Phaser game's parent, so a render can't make a second game, and remounts them for each new round; `listen(scene, event, handle)` removes the scene's listener when the scene shuts down; `useEvent` hands a component's handler its latest render, through React's `useEffectEvent`, so no handler reads stale state; and an event's value is typed as one primitive. What code can't hold (a panel's `pointer-events: auto`, hopon called outside a `setState` updater, its look) is in `references/phaser-panels.md`, about 2 KB, and a whole game that uses it is in `references/phaser-panels-example.md`, for the agent to read when it wants one. A Phaser game with only a score, lives or a timer has no React: it draws them in the scene.
- **A new game starts from a skeleton.** `node /opt/hopon/starter.js`, which make-game's new-game command runs after emptying the workspace, writes `index.html`, `vite.config.ts`, `tsconfig.json` and a `src/main.tsx` stub, the same for every engine, and refuses a workspace that holds a game. The agent keeps the three and writes its own `src/`. The title and hint are `hopon.title` and `hopon.hint`, set in `main.tsx`, not the page's `<title>`. The harness doesn't own the two configs: `vite.config.ts` is how the box tells a Vite game from an old one, and the check already reports a broken `tsconfig.json`.
- **One skill, with a guide per engine.** `make-game` is the only skill. Its `references/` hold `phaser.md`, `r3f.md` and `react.md` (and `phaser-panels.md` and `phaser-panels-example.md`, above), each with the project's files, the wiring to the scaffold, the engine's API and its traps at the box's version, touch controls, fair hits, performance, how to make the game look good, and one complete example that passed the box's check; `sound-effects.md`, a game's own sounds in `src/sfx.ts` played by the scaffold's `hopon.play`; and `music-synth.md` and `music-sf2.md`, the former music skills. `make-game` picks the engine and names the guide to read. The agent reads a guide with `read_skill_resource` (name `make-game`, path `references/phaser.md`), which `agents/harness/pi` already offers beside `activate_skill`; the Worker bundles each guide as a resource of make-game's manifest entry. So the agent always enters through make-game's rules: in P2's live runs it once loaded an engine skill alone and never saw the design, tests and music rules. `littlejs-api`, `dom-games` and `zzfx` are deleted. The skills' fingerprint is `v12`.
- **Phaser draws at the phone's pixel ratio, in CSS px.** Phaser 4 has no `resolution` setting, so the game is the viewport's size times `min(devicePixelRatio, 2)`, and the main camera zooms by the same factor. World coordinates are CSS px, which is what a test's taps are. The box's Chromium has a pixel ratio of 1, so a playtest draws 360 px wide and stays fast.
- **An old Draft is ported before it changes.** A workspace with a `game.ts` and no `vite.config.ts` is a LittleJS game (`game.ts` alone) or a plain-DOM one (with an `index.html`). `verify.js` refuses it, so `build` does too, with a sentence that points to make-game's "An old game". The agent ports it in the same run: LittleJS to Phaser, plain DOM to React, keeping `design.md`, `tests.json` and the music file, and the names the tests read, now in `hopon.testVars`. The old tests pass on the port, and the agent publishes the port on its own before it makes the change, since a port and a change together may not fit in one run's 20 steps, 4 builds and 300 s (30 steps, 4 builds and no time limit from ADR 0009). When a limit stops the run after that, the refusal tells the agent that the published Revision stays, and the agent tells the Creator to send the rest of the request again.
- **The box still builds a `game.ts`.** Its esbuild path, `/runtime/v4.js`, `/dom/v4.js` and their declarations stay, so the agent can playtest an old Draft before it ports it, and the harness's own cases keep their LittleJS fixtures. Every frozen `/runtime/v2–v4.js` and `/dom/v1–v4.js` stays served for published Games.
- **`/hopon/v1.js` is frozen.** Its sha256 is `HOPON_V1_SHA256` in `apps/maker/src/runtime.ts`, `build:runtime` refuses a changed scaffold, and the Worker serves it `immutable`. Before freezing it, the overlay's start tap stopped reaching the game: the overlay hides on its press, so the release, the touchend and the click that follow were landing on the game, and an r3f game that steers on `pointerup` changed lane at the start. The scaffold now swallows each once. It redraws the start screen whenever the game sets `hopon.title` or `hopon.hint`, and wraps a word too long for the screen. It plays sound effects, `hopon.play({freq, to, ms, wave, volume, delayMs})`, a synth of an oscillator or filtered noise through the music's AudioContext, which it now makes at the first touch whether or not the game has music (on `pointerup` and `touchend` too, since iOS starts audio only at a touch's end), so effects follow the mute and the pause and no game carries its own copy of the synth. The over screen's words moved to `hopon.text`, English by default, so a game in another language says them in its own. A change from here ships as `/hopon/v2.js`.
- **The playtest's clock runs every frame.** The fake clock derived its next frame from the current time, so a timer due at a frame's instant skipped that frame: a game with a 100 ms timer ran about a sixth slow. A callback that throws is now the page's error, which fails the check with its message, rather than a crash of the harness.

## Alternatives rejected

- **Either Phaser or React, never both.** The first version of this ADR had no way to put a React panel on a Phaser game, so a game with a world and menus got one of them. The published 大航海家 (Game 8), asked for in the style of a sailing and trading game, came out as React alone: menus, and a ship icon that slides between six ports by percentage.
- **React around every Phaser game.** Tried on a branch: `<Playfield>` in every Phaser game and its score moved to DOM. For the guide's runner it added 14% to the game's code (14.5 KB to 16.5 KB, two more files), 24% to the guide every run reads (35.7 KB to 44.2 KB), about 71 KB gzip of React to load, and five rules that exist only to keep React and Phaser apart, for a score label Phaser already draws. Code size is what a game costs (P5 trail, "Cost"). React is worth its bridge only where there is a panel.
- **Phaser's official React template as the skeleton.** Its five scenes include a menu and a game-over screen the scaffold already owns, its Boot and Preloader load image files the box doesn't have, its canvas is a fixed 1024 × 768, it runs under `StrictMode`, and its `log.js` calls a server on every build. Its `PhaserGame` component, which makes the game inside React, can make a second game when React mounts it again, and its `EventBus` leaves each scene to remove its own listeners; a first version of this guide kept both, with rules against those two traps.
- **A guide that teaches the bridge.** The first version was a 25.6 KB guide, 20.6 KB of it a whole example, whose prose told the agent how to write the bridge and which traps to avoid. A file the starter writes costs the agent nothing to write, and its API leaves no trap to avoid.
- **Panels drawn in Phaser.** Phaser has text, shapes and input but no buttons, lists, wrapping or layout, so a market is hand-placed rectangles and Texts, each needing `resolution` to be sharp.
- **Phaser 3.90 beside Phaser 4.** The model knows Phaser 3 better, but a second file needs its own specifier, types and URL, and the agent would still have to pick one. make-game's Phaser guide names the Phaser 3 habits that fail on 4 instead. The eval decides whether that is enough.
- **Phaser at a fixed 720 px width.** It is sharp on phones, but every tap in a test is half the game's coordinates, and a playtest in the box drew four times the pixels and took about 2.5 times as long.
- **Dropping the box's LittleJS build.** It would remove `runtime.js` from the image, but the agent could no longer play an old Draft before porting it, and two dozen harness cases would need new fixtures. Its cost is a few files in the image.
- **A round counter in the scaffold.** Each engine resets on the state's change from `over` to `play`, which the engine guides show. A counter would save a few lines a game, and the guides' examples already work without it.

## Consequences

- A Phaser game with panels loads React's two vendor files beside Phaser, and its run reads the panel rules beside the Phaser guide, about 38 KB against 36 KB, and the example when the agent asks for it. A Phaser game without panels costs what it did.
- Whether the agent picks the panel guide when it should, and lays its panels out right, is measured only by the guide's example in the box. No eval chat asks for a game with panels yet.
- New Games load `/hopon/v1.js` and the `/vendor/` files. A Game published before this change keeps its frozen scaffold.
- A change to an old Draft costs more the first time, since the agent ports it and builds twice. The port can change how the game feels. Its tests pass, and `check.test.ts` ports two fixtures, a LittleJS and a plain-DOM game, and plays them green. No eval chat ports a Draft, so a port's feel is checked only by hand, in P5's live lanes.
- The engine guides are long, about 1,000 lines each, most of it the example. A run reads one of them.
- A game costs about twice as much to make. A new game's code is about 2.5 times the bytes of a LittleJS `game.ts`, and the model's output and the context it rereads grow with it (P5 trail, "Cost").
- The eval's final checks build Vite games on the developer's machine, so `apps/maker` has the React and three types, and the playtest's Chromium uses SwiftShader there.
