# P4 trail: Vite games on shared vendor files

The decisions behind P4 of `maker-single-agent-vite.md`, in order. Each names what it changed and its evidence. P4 ships in two PRs: P4a (#221) lays the parts that don't depend on P3, and P4b switches the playtest and `build` to `vite build` on top of P3 (#220).

## P4a: vendor files, serving, scaffold, image

### Build

- **Branch.** `claude/p4a-vendor` from `origin/main` at `b933ddb`.
- **The vendor build runs on the host, not in the box.** `apps/maker/vendor/build.ts` uses Vite's library mode from `apps/maker`'s devDependencies, as `src/runtime.ts` builds LittleJS from `littlejsengine`. The bytes then come from `pnpm-lock.yaml`, and `src/vendor.test.ts` rebuilds them in about 0.6 s and fails when they differ from the committed JSON. The spike's `box/vendor.mjs` ran inside the box. Its approach carries over: the CommonJS entry that names React's exports, the `enforce: "pre"` sibling plugin that turns a sibling library into a re-export of its URL, three's missing default, and esbuild's minify.
- **A version comes from `apps/maker/package.json`, pinned exactly.** `three`'s `exports` hides its `package.json`, so the build reads the pin instead, and refuses a range.
- **Frozen like the scaffolds.** `FROZEN` holds every served vendor file's route and sha256. A build that differs from a frozen file fails, and a new file fails with the entry to add. The Worker's `api.ts` imports each JSON by name, and `worker.test.js` lists `src/vendor/` and asserts each is served, so a file without a route fails.
- **Phaser 4.2.1 only.** Shipping 3.90 as well would need an npm alias in the box (`phaser3@npm:phaser@3.90.0`), its own types and its own specifier, and P5 would still have to pick one per game. The spike ran 4.2.1, so it ships alone. P5's eval measures Sonnet on Phaser 4's API, and a Phaser 3 file can follow at its own URL.
- **`/hopon/v1.js`.** `apps/maker/image/hopon.js`, from the spike's `box/hopon.js` with the music and bridge of P3's `/dom/v4.js`: the page names `music.opus` on the script's `data-music`. It adds `hopon.title` and `hopon.hint` for the start screen, as the LittleJS scaffold has, `hopon.testVars` (a module can't declare a global), and the `hoponClock` frame counter the playtest reads. `ready()` sets `hopon.loaded`. Its types are `image/hopon-v1.d.ts`. `src/runtime.ts` freezes it as `HOPON_V1_SHA256` and writes `apps/worker/src/runtime/hopon-v1.json`. The box's playtest serves it at the same path. Freezing now means a change before any Game uses it still ships as v2. That cost is one more route.
- **CORS on every scaffold route.** The old `/runtime` and `/dom` routes share the loop and get `Access-Control-Allow-Origin: *` too. They are public scripts, so the header is harmless.
- **The image.** One `RUN` installs Vite 8.3.8, `@vitejs/plugin-react` 6.3.0, the five libraries and `@types/react`, `@types/react-dom` and `@types/three` into `/opt/hopon`, links `/opt/hopon/node_modules` at `/node_modules`, and removes Phaser's `src`, `tests`, `docs` and `changelog`. Debian's `/etc/profile` resets `PATH` in a login shell, which is what the model's bash runs, so `ENV PATH` alone left `vite` and `tsc` off it. `/etc/profile.d/hopon.sh` adds them. Measured: `bash -lc 'command -v vite'` printed nothing before that line.
- **The box's game CSP moved to `page.ts`.** `check.test.ts` needs it, and it can't import `helpers.js` from TypeScript. `helpers.js` imports it from there.

### Verify, unit

- `pnpm check` green at `2220f42`.
- Mutations, each red then restored. A changed byte in `react-19.3.1.json` fails "the Worker serves each vendor file as it was frozen" and "the vendor build makes the bytes the Worker serves". `phaser@4.2.0` in the Dockerfile fails "the box installs the versions the vendor files are built from". A changed constant in `hopon.js` fails "the Worker serves the Vite games' scaffold the box serves", and `build:runtime` refuses with "/hopon/v1.js is frozen and this build differs from it". Removing the `Access-Control-Allow-Origin` line from `api.ts` fails the worker test "vendor:".
- `HOPON_BOX_IMAGE=hopon-box:p4a pnpm -F maker test`: 42 of 42, on an image built from this head (arm64, local Docker). The new cases write three fixtures (`apps/maker/fixtures/vite/`: a React quiz, a Phaser scene, an r3f spinner) into a box started with `--network none`, run `tsc -p . && vite build` in a login shell with the libraries external at their vendor URLs, then serve the build, `/hopon/v1.js` and the vendor files from a Node HTTP server in the box under the box's game CSP. Chromium loads each with no console error, `origin` is `"null"`, the game calls `ready()`, a tap takes the overlay from start to play, and the engine's loop ran. Each library's file loads once, and each game's own files are under 10 KB gzip.
- **CORS is enforced on a sandboxed page's modules, in Chromium.** The first version of the no-header case served through Playwright's `page.route`, and the page still loaded: routing skips the CORS check, which the plan's Appendix A suspected. Served by a real HTTP server, the same page without the header fails to load its modules. The case stays in `check.test.ts`.

### Sizes

- Image, arm64, local Docker, measured against main's Dockerfile built from the same context: `docker image inspect .Size` 501.8 MB to 535.5 MB, +33.7 MB. `docker image ls` 1.81 GB to 2.02 GB on disk. `/opt/hopon/node_modules` is 211 MB, Phaser's types 54 MB of it. The spike's +43.6 MB was amd64 under Rosetta, with its own measure. Not measured here: the amd64 image Cloudflare runs.
- Worker: `wrangler deploy --dry-run` uploads 10,520 KiB, 2,261 KiB gzip.

### Not done in P4a

- The playtest and `build` still bundle with esbuild. P4b switches them to `vite build`, serves the vendor files in the box's playtest, and advances fake frames while a game loads.
- The box's playtest serves neither `/hopon/v1.js` nor a vendor file, since no harness path builds a Vite game yet. See round 2.
- iOS and Android WebViews: whether they enforce CORS on these modules and share the HTTP cache across feed games stays unproven. The plan's lanes 2 to 5 cover it in P4b.

## P4a round 2: on top of P3, and the review's fixes

- **Rebased onto `d5da5de` (P3, #220).** Conflicts in the Dockerfile's `COPY` (both lists, joined), `helpers.js`, `page.ts`, `check.test.ts`'s imports, `runtime.ts` and `api.ts`'s scaffold routes (`/runtime/v4.js`, `/dom/v4.js`, `/hopon/v1.js` and the vendor files, all kept). P4a had moved the box's game CSP into `page.ts` with its pre-P3 value. P3's value wins there (`'self'` for styles, images, fonts and fetches), and `helpers.js` imports it. `check.test.ts`'s Vite fixtures load under that value.
- **`/hopon/v1.js` is not frozen yet.** The operator's call: it freezes when the first real Game uses it, in P5. Until then nothing can depend on its bytes. `runtime.ts` drops `HOPON_V1_SHA256` and still writes the Worker's copy (`runtime.test.ts` fails when it is stale). The Worker serves it with `Cache-Control: no-cache` rather than `immutable`, so a change before P5 reaches every page. The box's playtest stops serving it, so a page that loads it gets a 404, a console error, and fails the check: no Revision can load it. `check.test.ts`'s "a page that loads /hopon/v1.js fails the check" was red on the image from the rebased head (the page passed and became a Revision) and is green now. The Vite fixtures still load it: `fixtures/vite/load.mjs` reads `/opt/hopon/hopon.js` itself.
- **The vendor files go out pre-compressed.** `build.ts` commits each as the base64 of its gzip (level 9), and the Worker decodes it once per isolate and sends those bytes with `encodeBody: "manual"` and `Content-Encoding: gzip` when the client takes gzip, or pipes them through `DecompressionStream` for one that doesn't. The Workers runtime no longer gzips 1.7 MB of Phaser on each request. `FROZEN` still holds the sha256 of the code, and another zlib may gzip the same code to other bytes, so the build rewrites a committed file only when it unzips to different code. That keeps `build:vendor` from dirtying the tree on another machine. The committed files shrink from 2.8 MB to 0.93 MB. `worker.test.js`'s "vendor:" case fetches each file with and without `Accept-Encoding: gzip` and checks the sha256 of the unzipped body against `FROZEN`. It was red before the change ("incorrect header check": Node's `Response` doesn't compress, so the body was the code under a gzip header).
- **`NODE_ENV=production pnpm -F maker build:vendor` reproduces the frozen bytes.** React's CommonJS index loads its development or production build by `NODE_ENV`, and the development one also exports `act` and `captureOwnerStack`. The frozen files were built with those names, so `build.ts` reads the names with `NODE_ENV=development` and puts the shell's value back. The bundled code was production before and still is (Vite's `define`). Measured: the build failed with "/vendor/react-19.3.1.js is frozen and this build differs from it" under `NODE_ENV=production` before, and passes after. `vendor.test.ts` builds React in a child process with `NODE_ENV=production` and checks it against `FROZEN`.
- **The 5 MB caps hold.** `job.ts` listed `dist/` as `%s %f\n`, so a file name holding a newline split into lines whose size parsed as `NaN`, and a `NaN` total passes `bytes > MAX_BUILT_BYTES`. It now lists with `%s %f\0` and splits on NUL, and the whole name then fails the served-name rule. `check.test.ts` leaves a process writing a 6 MB file, `a\nxy z`, `a` and `z` into `dist/`: before, the check passed and returned the 6 MB file; now it fails with "rename". `job.ts` also measures what it read, since a file can grow between `stat` and the read: the packed source and `dist/`'s files, each against its 5 MB cap. Two cases hand the harness a 6 MB read of each. Before, a grown `dist/game.js` became a Revision and a grown source failed in `tar`; now each fails the check with the size.
- **The Dockerfile check matches whole install tokens.** `vendor.test.ts` reads each `package@version` token of the Dockerfile and checks the five libraries, `vite` and `@vitejs/plugin-react` against `apps/maker`'s exact pins, and `@types/react`, `@types/react-dom` and `@types/three` against their library's major.minor, as DefinitelyTyped versions them. The `@types` aren't pinned in `apps/maker`: adding them churned unrelated peer resolutions in `pnpm-lock.yaml`, and the major.minor rule is the one that matters.
- **Left for P4b.** A game's own files already carry `Access-Control-Allow-Origin: *` from P3 (`gameFile` in `api.ts`, for published Games and Draft previews alike), so a game's module scripts load from its sandboxed page. But the Worker serves a game's files by flat name only (`[\w.-]+`), and `job.ts` reads `dist/` at depth 1, while Vite writes `dist/assets/` by default. P4b's Vite config needs `build.assetsDir: ""` or the Worker a nested route. Pause enforcement in Phaser and r3f games stays P4b's too.

## P4b: the box builds and plays Vite games

### Build

- **Branch.** `claude/p4b-vite-build` from `origin/main` at `f4ba760`.
- **A workspace with a `vite.config.ts` is a Vite game.** One file, checked once, and no LittleJS or plain-DOM game has one. The other rule on offer, a `package.json` beside an `index.html` with a module script, needs the page parsed, and a plain-DOM game already has an `index.html`. P5's skill has the agent write `vite.config.ts` with `@vitejs/plugin-react`. Without it, a workspace stays on today's esbuild path, so LittleJS and plain-DOM games build as before. `verify.js` takes a `vite.config.ts` in place of `game.ts`.
- **The harness's settings win over the game's config.** `helpers.js` calls Vite's `build()` with the workspace as the root: `base: "./"`, `outDir: "dist"`, `assetsDir: ""`, and every vendor specifier external at its `/vendor/` URL. Vite merges an inline config over the config file, so the game's `vite.config.ts` needs only its plugin. Every file lands flat in `dist/`, which is all `job.ts` reads and all the Worker serves of a Revision. The playtest now serves only `dist/`'s top level too, so a file a page needs from a subdirectory fails the playtest rather than going missing from the Revision.
- **Typecheck as `tsc -p .`.** The TypeScript API parses the game's `tsconfig.json`, adds the image's `hopon-v1.d.ts` and `assets.d.ts` as root files, and reports the diagnostics of the game's own files, as the game.ts path does. A missing `tsconfig.json` is an error. The libraries' types resolve through `/node_modules`.
- **A vendored library built into the game fails.** The build's chunks list their module ids. One under `/node_modules/<pkg>/` for a vendored package (react, react-dom, phaser, three, @react-three/fiber) is a second copy beside the shared file: "react built into the game: import only react, react/jsx-runtime, which load the shared /vendor/ files". three's addons (`three/examples/`) are allowed, since they import three by name and so use the shared one. Measured: `import "react/jsx-dev-runtime"` fails with that message, and an `OrbitControls` import builds and plays.
- **The music.** `music.opus` is copied into `dist/`, and `page.ts`'s `viteHtml` names it on the `/hopon/v1.js` tag's `data-music`, as P3 does for `/runtime/v4.js` and `/dom/v4.js`.
- **The box's vendor files are the Worker's bytes.** `build:runtime` writes `image/vendor.json` (gitignored, like `runtime.js`): each route's committed gzip, copied from `apps/worker/src/vendor/`, and the specifier map. The Dockerfile copies it to `/opt/hopon`. The playtest gunzips it once, as the Worker does for a client that doesn't take gzip. A docker case checks each route's sha256 against `FROZEN` and the map against `vendorPaths()`.
- **Playtest.** For a Vite game the playtest also serves `/hopon/v1.js` and the vendor files, under `GAME_CSP` with `Access-Control-Allow-Origin: *`. A LittleJS or plain-DOM page that loads `/hopon/v1.js` still gets a 404. While a Vite game loads, the fake clock moves one frame per 10 ms poll until `hopon.loaded` (the spike's approach: r3f measures its canvas on a timer before it mounts). A game that hasn't called `hopon.ready()` within 10 s fails with that sentence. Tests read `hopon.testVars` when there's no global `testVars`.
- **Pause.** `hopon.js` already exposed `paused` and `subscribe`, and the feed's messages already reach listeners, so it doesn't change. The Phaser fixture follows `hopon.paused` with `game.pause()` and `game.resume()`, and the r3f fixture sets `frameloop="never"`. A test's inputs now take `{"type": "pause"}` and `{"type": "resume"}`, which dispatch the feed's message in the page and take no game time, so a fixture's `tests.json` checks that its frame counter stops while paused and runs again after. P5's skill can teach the same test.
- **The fixtures are workspaces.** Each of `apps/maker/fixtures/vite/{quiz,phaser,r3f}` now has its `vite.config.ts`, `tsconfig.json` and `tests.json`. The Phaser square turns, so the start and end screenshots differ. The quiz's options sit at fixed bands so its test can tap the right one.
- **The manual-gzip guard runs on workerd.** `apps/worker/test/maker.test.js` already runs the Worker under `wrangler dev` in `pnpm check`, so CI runs it. Its new case fetches each `/vendor/` file with `Accept-Encoding: gzip` through `node:http`, which doesn't decode, and checks that one gunzip gives the frozen sha256.
- **The fake publishes a Vite game.** `test/maker/worker.ts`'s fake playtest builds a Vite-shaped `dist/` (the page and `index-B1x2.js`) when the workspace has `vite.config.ts`, and a `vite` script writes one. The new case checks the Revision's `source.tgz` names, the page's tag, and that the preview serves the module with `Access-Control-Allow-Origin: *`.
